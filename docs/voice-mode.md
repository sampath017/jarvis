# Hands-free voice in the existing Chat screen

Tap the microphone beside the message box once to start listening and again to stop. There is no start/stop menu. Enabling the microphone enters wake-word standby. Say `Hey Jarvis`, wait for `Hi, how can I help you?`, then speak naturally. Microphone permission must already be granted or approved on first use. Voice and activity monitoring share one ongoing Jarvis notification. It shows the voice state and a Stop listening action while the microphone is active; Android also displays its microphone privacy indicator. Stop from the microphone button or notification, say `stop listening` during an activated conversation, or turn the Jarvis assistant off.

Once started, the native microphone service continues when you go Home, use another app, or lock the screen. Flutter does not need to remain visible.

Wake phrases include `Hey Jarvis`, `Hi Jarvis`, `Hello Jarvis`, `Hey, what's up Jarvis?`, and `Jarvis`. Idle Vosk recognition uses a focused greeting grammar with an unknown-speech alternative; the matcher accepts the complete word `Jarvis` anywhere in a recognized phrase. Replies are spoken using an installed offline English Android TTS voice. After a reply, a two-minute idle window allows conversation without repeating the wake phrase. Say `end conversation`, `goodbye`, or `go to sleep` to return to wake standby; `stop listening` disables the microphone. The `New voice conversation` voice command creates a new voice thread. Voice exchanges appear as `Voice · date` in the existing chat history; no separate voice screen exists. Typed threads are not reused or silently overwritten.

## Local audio and service lifecycle

The official Apache-2.0 `vosk-model-small-en-us-0.15` model handles offline wake detection and local turn/control recognition. Wake detection immediately plays the offline greeting; wake audio is not sent to cloud transcription. Activated command turns use `openai/whisper-large-v3-turbo` through OpenRouter. There is no on-device general conversational language model: without connectivity, wake/greeting and locally recognized stop/end controls remain available, while questions receive a brief offline notice and return to standby.

This is a foreground software recognizer, not privileged sensor-hub/DSP detection or speaker authentication. One AudioRecord owner uses `VOICE_COMMUNICATION` and enables Android AcousticEchoCanceler when available. Silero VAD v5.1 detects speech; local Vosk partial text is checked against the current reply to reduce self-interruption. About 256ms of sustained speech plus non-echo recognized text is required to interrupt; without AEC, the text gate is stricter. A rolling RAM buffer preserves up to 1.5 seconds of the interruption. Actual double-talk performance depends on the phone, speaker volume, room and voice; availability of AEC is not proof of reliable echo removal.

Commands end after roughly 800ms without speech, with a 60-second transport bound. Idle listening returns to wake standby after two minutes. Audio is not written to disk by the app/backend; provider retention is governed by the routed provider. The API key stays on the backend.

Model weights and the downloaded archive live under ignored `backend/models/voice/`. Android assets include only `backend/models/voice/android/`; the model is unpacked into the app's own files on first activation. The official archive is from https://alphacephei.com/vosk/models/vosk-model-small-en-us-0.15.zip with SHA-256 `30f26242c4eb449f948e42cb302dd7a686cb29a3423a8367f99ff41780942498`. Android uses Vosk 0.3.75 and JNA 5.18.1 from the official demo's dependency coordinates. Preserve their Apache licenses/attribution when distributing.

Enable listening from a visible activity. The enabled choice is remembered: reopening Jarvis restores listening directly into wake-word standby if microphone and notification permissions remain granted and assistant power is on. Explicit Stop (button, notification or voice command) and assistant power-off clear that choice. Android microphone foreground-service restrictions prevent arbitrary background/boot activation; the service deliberately does not silently restart after process death, app force-stop or device reboot until Jarvis is reopened. OS/OEM killing and microphone contention can interrupt listening. Real-user wake accuracy and battery performance remain device measurements, not promises.

## Command and storage flow

`offline wake -> local greeting -> conversation audio -> /voice/transcribe -> OpenRouter Whisper -> transcript -> private command SSE -> existing shared agent -> phone action receipt -> local SQLite commit -> Android TTS`.

During a reply or a pending network turn, a detected interruption stops TTS, invalidates old playback callbacks, and disconnects the old client. The microphone retains the new utterance rather than resetting it. Late callbacks are scoped to their original turn and cannot speak over the new one. Disconnecting an in-flight command does not undo actions already performed by the backend; interrupted requests are not automatically replayed.

The native client uses the same `/commands/stream` protocol, immutable request IDs across reconnects, and private device session capability as text chat. Voice messages use a dedicated `voice_...` thread in the same `chat_sessions`/`chat_messages` SQLite tables. Complete current-voice-thread history is sent; it is not merged with an unrelated typed thread. Clock actions execute natively even when the Flutter view is not visible. Notes, reminders and selected scoped records use the same phone-owned commit protocol.

Account connections, Health Connect/file tools and approval-requiring operations can still require opening Jarvis; unsupported native voice actions return explicit unavailable/needs-user-input results instead of fabricated success. Understanding/replies require backend connectivity; offline recognition does not make the remote agent available offline. Microphone processing continues during TTS to allow interruptions, with local echo rejection. The full text is retained even if speech playback is interrupted. Interrupted requests retain their IDs and uncertainty; do not blindly replay them with new IDs.

Turning assistant power off stops the microphone/voice service. Clock and Notes remain independent and available locally.

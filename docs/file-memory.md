# File memory and native analysis

## Drive content index

Chat bubbles and history day labels display fixed IST (UTC+05:30), independent of the phone's timezone. Persisted chat instants use UTC. Independent file searches/analyses emitted in one planner turn share one device round trip and run two at a time; writes remain ordered and retain approval rules. Drive access/version checks run four at a time. Model and reasoning settings remain unchanged. The measured 130-second resume/identity query spent about 59 seconds in six planner calls, 27 seconds in two searches and 40 seconds in five file-read steps; these were the principal bottlenecks.

File search reads indexed contents by default. It combines Drive full-text/filename matches with semantic candidates, verifies current Drive access and version on the phone, then retrieves relevant passages for those verified file IDs/versions in one batch. The original information need is preserved separately from short discovery keywords. Explicit filenames-only requests disable passage reading. Missing or media-only passages require reading relevant originals before claiming contents or absence; incomplete indexing is not proof that a document does not exist. Workspace URLs share one validator across chat requests and file registration. Retrieved passages require answer synthesis and never bypass the assistant as a completed native answer.

Interactive content-search embedding calls have a 25-second HTTP timeout. A cold model can take longer to load; the app then falls back to live Drive filename search with an explicit notice. Background file indexing retains its longer deadline. Measured model loading on the CPU deployment was approximately 38–49 seconds; provisioning can add more time, so scale-to-zero does not guarantee a 30-second cold response.

The app requests `drive.readonly` for discovery, `drive.file` for writes to files created/shared with Jarvis, and `forms.responses.readonly` for Forms answers. Existing users approve the expanded Google consent once. Live Drive search no longer filters to Jarvis-tagged files. Expired download tokens are refreshed once; missing files and permission/download restrictions are reported separately. Direct native reading still uses PDF exports for Google Docs, Sheets and Slides.

`jarvis-embedding` runs EmbeddingGemma 2 on CPU in Cloud Run (`asia-south1`): 4 vCPU, 8 GiB, concurrency 2, minimum instances 0, maximum instances 2. Its endpoint requires IAM authentication and grants invocation to the backend service identity. The 512 MiB backend fetches an IAM ID token for the embedding service URL, sends bounded inputs to `/embed`, and explicitly supplies returned 768-dimensional vectors to Chroma Cloud for upsert/query. Chroma does not generate embeddings. Credentials are held in Secret Manager. Model weights are baked into the CPU image; CPU TorchCodec, torchvision, and FFmpeg enable all media encoders. The build smoke test covers text, image, audio and video.

Indexing submits every accessible Drive entry without application caps on total file size, PDF pages, or chunks. Android streams originals or complete Office exports (DOCX/XLSX/PPTX) into private Mumbai Cloud Storage in 8 MiB upload pieces. Keep Jarvis open during submission; page checkpoints and source-version records avoid repeating completed submissions, while interrupted individual uploads restart. A Mumbai Cloud Run Job (2 vCPU, 4 GiB) reads staged sources and continues processing after the phone closes. Successfully indexed staging copies are deleted; originals remain in Drive. Failed sources remain staged for retry. Google export/API limits and available service resources still apply.

PDFs use text passages or rendered scanned pages; audio uses 30-second segments and video uses 10-second visual segments (video audio is not indexed in this version). Two units per embedding batch bound memory without limiting total file length. Office readers include tables, hidden sheets, formulas, comments, slide notes and embedded media. Legacy formats use passive decoding or macro-disabled conversion. ZIP, TAR, RAR, 7z, compressed and nested archives are read without extracting untrusted member paths into the server filesystem. Android manifests, executable metadata, binary strings and SQLite rows are indexed. Forms questions and paginated responses are read on the phone; drawings export as PNG and shortcuts resolve to targets. Every source gets content, partial coverage, or metadata-only coverage with a reason. Encrypted, damaged or inaccessible content remains visible as needing attention. Unknown Google-native formats without a readable API export retain metadata. The results screen paginates all outcomes. Chat, search and telemetry remain concurrent with the worker. Cloud Run Jobs consume compute while executing; staging storage remains billed while retained.

Deploy the embedding service with `python -m scripts.deploy_embedding`, then the staging bucket, backend, and worker with `python -m scripts.deploy_drive_index` from the backend environment. Bulk indexing control routes retain phone capability checks and do not consume chat's request-rate allowance.

The Chroma collection `jarvis-drive-eg2-768-v1` is scoped by the random phone capability and Google account. Partially indexed versions are excluded from search. Successful versions replace stale chunks. The phone rechecks Drive access and version before returning matches or indexed passages for Office, archives, text, Forms, binary information and large files. Passages carry locators and coverage and are untrusted data, never instructions. Selected passages are not a complete-file inspection. Updating the model or preprocessing requires a versioned index and re-embedding. Scale-to-zero removes idle compute after shutdown; storage remains billed and cold-start/large-media latency is not guaranteed to stay below 30 seconds.

Google connections default to **sampathkovvali@gmail.com** on this phone. Attach a PDF, image or video in chat; Google consent opens if connection is needed. The text you send is remembered as your description. The user's send action authorizes the upload, and file questions authorize native analysis. Neither operation asks for an additional Jarvis confirmation.

Settings keeps a collapsed **Connected accounts** entry for account status, calendar choice and disconnect controls. Healthy accounts do not show a reconnect button. At app startup, missing local connections attempt to reuse an existing Google grant silently, then verify API access before saving the connection. No consent dialog opens automatically. An explicit disconnect disables this restoration until the user connects again. App updates retain preferences; after a full reinstall, restoration depends on the Google account/grant and Android's restored data. When consent is required, Connect/Reconnect remains available. Tokens stay in memory on the phone.

Ordinary attachments (up to 250 MB) are uploaded directly from Android to a private **Jarvis Upload Cache** folder using the limited `drive.file` scope. Explicit “save/upload to Google Drive” requests use the **top level of My Drive**. A later explicit save moves the cached file into My Drive while preserving its ID/link, without uploading a duplicate. Cache files remain available for follow-up questions; there is no automatic deletion policy. Firebase Firestore stores the name, user description, MIME type, size, account, creation time, storage category and Drive ID/link, never raw files. Local metadata and upload receipts support offline recall and safe retries. Temporary selected-file copies are removed after a confirmed upload and Firebase save. Existing files remain where they were until an explicit save request.

Ask to find a remembered file or ask a question about its contents. Metadata search requires no content sharing. Requested native analysis has standing permission and shares the file with the model without another dialog. GLM 5.3 Flash remains the chat/image/video model. PDFs use Gemini 3.8 Flash with OpenRouter's native PDF engine; no PDF text extraction or OCR pipeline is used. Other important actions, including calendar changes, deletion and public sharing, retain their approval guardrails.

For analysis, Android reads the approved original using its local Google token, then sends at most 20 MB through Jarvis to OpenRouter. Raw bytes are transient in memory and are never written to Firebase or backend disk. Firebase may retain the derived answer and a receipt. Provider data handling follows the configured OpenRouter/provider policies. Larger originals remain saved in Drive; use a smaller file or video clip for analysis.

A random 256-bit phone capability protects the Firestore metadata namespace independently of the backend's existing shared local user. It survives Drive disconnect and enables recall across chats on this phone; it is not cross-device Google identity authentication. Google tokens stay on the phone. Disconnect stops Drive reads/writes; saved originals and remembered metadata remain. Request/action receipts prevent automatic repeated uploads and paid analysis retries after uncertain outcomes.

## Request routing

Ordinary attachment uploads are silent; chat shows the answer and upload progress, not the internal cache folder or a storage link. Explicit My Drive saves still receive a save confirmation. Existing cache notices are hidden from the chat and excluded from model history.

New attachments use a compact GLM routing prompt containing their references and only file tools. Mixed requests hand off to the full assistant. GLM's existing reasoning effort and completion allowance are preserved. A successful single-file analysis of the complete original question is returned directly; partial analyses, errors and mixed actions still require further handling. Native analysis rejects incomplete provider replies and has a two-minute total provider deadline without automatic paid retries.

The Tier 2 GLM orchestrator selects tools from the user's question and relevant conversation turns. User commands load only chat history and file references first. They do not automatically read mobility sessions, reminders, GPS, nearby places or activity history. A resume follow-up can reuse job dates from the preceding answer. A question requiring the file uses native analysis. `get_current_location` requests a fresh phone fix only when selected for a location-dependent task, and `recall_context_history` retrieves historical activities only when requested. Background sensor/context-event processing is unchanged. Location permission remains an Android requirement when location is actually needed.

Simple activity recaps such as “What I did today” render the verified history result directly after retrieval, without another model generation. The formatter requires complete evidence for the requested window, preserves IST times and recording gaps, and does not infer sleeping or work from stationary phone state. Complex activity questions still use the agent. The model client makes no automatic transport retry; partial tool arguments remain unexecuted.

## Digital wellbeing

Reports sum foreground app activity from local midnight to the requested cutoff in Asia/Kolkata. The 11 PM report ends at 11 PM; a report requested now ends now. Android activity resumes that occur before unlock or screen-on are retained and counted only once the phone is interactive and unlocked. Home/System UI/Glance lock-screen activity is excluded. Saved reports from the previous calculation version are recomputed while Android event history remains available. Android Usage Access must remain enabled; missing history is reported as unavailable.

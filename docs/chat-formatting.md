# Rich chat replies

Assistant replies use GitHub Flavored Markdown rendered by [flutter_markdown_plus](https://pub.dev/packages/flutter_markdown_plus). The renderer supports headings, paragraphs, emphasis, lists, blockquotes, inline code, code blocks, tables, and source links. Tables scroll horizontally on small screens. Text stays selectable, code has its own copy button, and the response copy button retains the original Markdown. User messages remain literal text. Earlier saved assistant replies use the same renderer without changing stored content; legacy bullet characters are normalized for display.

The backend preserves Markdown rather than stripping headings and emphasis. Its instructions choose tables for useful comparisons and charts for supported numerical comparisons, trends, and parts of a whole. Ordinary replies remain short prose when a visual adds little. Public links open through [url_launcher](https://pub.dev/packages/url_launcher) only after a tap, using HTTP/HTTPS. Embedded images are shown as links rather than automatically loading external or local content. No HTML or JavaScript executes in chat.

Charts use [fl_chart](https://pub.dev/packages/fl_chart) and a fenced `chart` JSON block:

````text
```chart
{"type":"bar","title":"Walking","unit":"minutes","labels":["Mon","Tue"],"series":[{"name":"Walking","values":[20,35]}]}
```
````

Supported types are `bar`, `line`, and `pie`. A reply can show up to three charts. Each chart accepts up to 24 labels and three series, with a matching finite numeric value for each label. Pie charts require one nonnegative series, a positive total and at most 12 labels. Titles, labels, units, magnitude and payload size are bounded. Invalid blocks remain readable code instead of producing a graph or crashing. Chart data is available in an expandable table for exact values and accessibility. Only verified values should be plotted; incomplete data, ranges and uncertain prices should use a qualified table instead. A chart never creates missing records or fills gaps with invented data.

Coverage: `tests/android/ui/chat_message_content_test.dart`, `tests/android/ui/chat_rich_content_test.dart`, and `tests/backend/test_rich_reply.py`. Set `JARVIS_CHAT_PREVIEW` to an artifact PNG path while running the rich-content tests to save a sample-data rendering for visual review.

All natural-language chat requests reach the LLM. Android app usage and Health Connect have explicit tools, `get_app_usage` and `get_health_records`, separate from movement/location's `recall_context_history`. The model chooses the source and date range, receives structured records through the authenticated device session, and writes the final answer. The phone no longer intercepts questions with screen-time or health keywords. File and movement results also return to the model for synthesis. Every request reads the complete current chat from SQLite, independently of UI scroll pagination, and sends every user/assistant turn with absolute timestamps. There is no 24-message or 16,000-character cutoff, including on attachment-routing calls. The current request is sent once, separate from history. User-message numbers and explicit IST dates/times ground questions about message order. Visible application errors are included and marked; hidden attachment-storage notices remain internal. Other-chat recall cannot establish this chat's order or timestamps. If the full conversation exceeds the provider's context window, the request fails clearly rather than silently discarding older messages. If the subject is ambiguous, the model should ask rather than switch datasets.

`render_chart` validates the same native chart contract before the model includes its returned Markdown. App-usage tools retain exact milliseconds and aggregate excess app categories without dropping their time; the model converts numeric durations rather than rounding earlier prose. Dates use Asia/Kolkata with inclusive ranges of at most 31 days, and results are bounded. Health reads require existing Health Connect permissions and distinguish steps from recorded sleep sessions. Missing days and denied permissions are reported explicitly, never inferred as zero or replaced with another dataset. Overview/report screens remain local UI. No OS permission is granted by an LLM tool.

New conversational capabilities should follow this tool pattern: register a typed tool in `build_agent_tools`, describe its source and units, execute native reads through `PhoneDataExecutor` and the private request session, and return structured evidence to the model. Keep permission checks and cancellation in the executor. Add service tests and a model/tool-loop regression rather than another keyword answer branch in the chat screen.
